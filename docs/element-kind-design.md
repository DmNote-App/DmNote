# 요소 종류 정의 체계 설계 문서

> 작성일: 2026-10-28
> 목표: 요소 종류 하나를 정의 하나로 만들고, 저장·검증·편집 계산·그리기·패널을 그 정의에서 이끌어 낸다. 기존 종류도 모두 옮기고, 나중에 같은 정의를 플러그인 공개 API로 연다.
> 상태: **방향 확정** / 새 구조 1차 구현(커서 트래커까지), 내장 종류 이전 전
> 관련 브랜치: `refactor/element-kind-registry` (1~3단계 레지스트리, main 반영)

---

## 1. 배경

- 새 캔버스 요소 종류를 추가하려면 백엔드 36개·프론트 85개 파일을 고쳐야 했다(1단계 착수 전 조사).
- 1~3단계에서 종류 목록과 연결 지점을 표로 모았다. 그래도 저장 모양, 검증, 패널, 창별 그리기는 종류마다 따로 남아 있다.
- 같은 내용을 TS와 Rust에 두 번 적는다. `KeyPosition`의 칸 77개가 [Rust 구조체](../src-tauri/src/models/element_positions.rs)와 [TS zod 스키마](../src/types/key/keys.ts)에 각각 있고, 코드 생성 도구는 없다. 두 벌을 맞추는 동기화 데이터가 `tests/fixtures/`에 9개 있지만(오류 코드, 편집 연산, 종류 목록, 회전·스프라이트 계산 등), `KeyPosition` 칸 일치는 그중 어디에도 고정돼 있지 않다.
- 편집 화면과 오버레이가 같은 요소를 따로 그린다. 그리기 핵심([GraphPanel](../src/renderer/components/shared/graph/GraphPanel.tsx), [KnobFace](../src/renderer/components/shared/KnobFace.tsx))은 공유하지만, 데이터를 모으고 겉모습을 조립하는 바깥 코드는 창마다 있다. 그래프·노브 모두 오버레이 파일(`OverlayGraphItem.tsx`, `OverlayKnobItem.tsx`)을 고친 커밋 20개 중 14개가 짝이 되는 편집 화면 파일도 같이 고쳤다(`git log --follow` 기준). 저장소 전체 리팩터링·포맷·폴더 이동·용어 변경·되돌리기 커밋을 빼면 그래프는 12개 중 6개, 노브는 16개 중 10개다.
- 같은 값을 여러 곳에서 다룬다. 그래프 속도 범위(500~60000ms)가 단일 선택 패널, 다중 선택 패널 쪽 2개 파일, 오버레이 그리기에 따로 적혀 있고 백엔드는 검사하지 않는다. 다중 선택 패널은 선택 조합마다 손으로 고른다([selectionPanelRoute.ts](../src/renderer/components/main/Grid/PropertiesPanel/selection/selectionPanelRoute.ts)).

## 2. 목표와 원칙

### 목표

1. **정의 하나**: 종류를 만드는 사람은 정의 파일 하나만 쓰고 동작에만 신경 쓴다(`defineElementKind` 형태).
2. **전부 이전**: 키·스탯·그래프·노브·스프라이트도 같은 정의로 옮긴다.
3. **선언 기본, 표현 제약 없음**: 선언이 기본이고, 선언으로 안 되는 부분은 코드로 끼운다. 선언 때문에 표현할 수 없는 형태가 생기면 안 된다.
4. **나중에 공개**: 지금은 내부 전용이다. 나중에 같은 정의를 플러그인 공개 API로 열고, `defineElement`는 그 위의 껍데기로 남긴다.

### 원칙

- 검증은 백엔드 한 곳에서, 스키마를 보고 한다.
- 쓰기는 엄격하게, 읽기는 너그럽게 한다. 모르는 칸은 지우지 않고 보존한다.
- 거부와 정규화는 값 종류 단위로 정한다.
- 일관성은 구조로 지킨다. 구조로 막을 수 있는 것을 규칙으로 막지 않는다.
- 모든 구조는 원본이 하나다. 반대편은 원본에서 만든 것을 읽는다.
- 공개 약속(플러그인 API, 사용자 CSS)은 겉모양을 유지하고 안쪽만 바꾼다.
- 앱 내부는 막지 않는다. 플러그인과 종류 코드는 지금처럼 앱 API와 내부에 닿을 수 있다.
- 화면에 먼저 반영하는 편집(낙관 적용)은 유지한다.

## 3. 결정 사항

### 3.1 저장 모양 — **[확정]**

- 탭(장면)마다 요소 트리 하나를 둔다. 목록 순서가 곧 겹치는 순서다.
- 그룹은 레이어 정리용 폴더이고 중첩할 수 있다. 일반 그래픽 편집 도구와 같다.
- 지금의 종류별 배열(`keyPositions`, `statPositions` 등)과 `keys[mode][i]` ↔ `keyPositions[mode][i]` 인덱스 결합은 없어진다.
- 이전할 때 그룹 구성은 유지한다. 겹치는 순서에서 흩어져 있던 그룹 멤버는 한곳으로 모은다. 그래서 일부 화면은 겹침 순서가 달라질 수 있고, 레이어 탭에서 다시 맞추면 된다. 이 변화는 받아들이기로 했다.
- 참고: 지금 레이어 탭은 흩어진 그룹을 실제 순서와 다르게 보여 주는 기존 버그가 있다.

### 3.2 요소 구조 — **[확정]**

요소 하나는 네 부분으로 이뤄진다.

| 부분      | 내용                                                                                                      | 정하는 쪽          |
| --------- | --------------------------------------------------------------------------------------------------------- | ------------------ |
| 공통 정보 | id, 종류, 위치·크기·회전, 이름, 숨김, CSS 클래스                                                          | 앱 (Rust 구조체)   |
| 기능 묶음 | 배경·테두리, 글꼴, 이미지, 노트, 카운터, 사운드 등. 종류가 쓰는 것만 붙는다. 묶음 하나가 패널 섹션 하나다 | 앱 (Rust 구조체)   |
| 고유 값   | 그래프 모양·속도, 노브 감도처럼 그 종류에만 있는 값                                                       | 종류 정의의 규칙표 |
| 입력      | 키 슬롯, HID 축, 마우스 이동 등                                                                           | 앱 (Rust 구조체)   |

- 백엔드가 자주 읽는 값은 고유 값에 두지 않고 공통 정보·기능 묶음·입력으로 올린다. 예를 들어 키 사운드는 백엔드가 직접 재생하므로 사운드 묶음에 둔다.
- 묶음 경계(예: 눌림 상태 색을 어느 묶음에 둘지)는 세부 설계에서 정한다.

### 3.3 검증 — **[확정]**

- 공통 정보·기능 묶음·입력은 Rust 구조체로 검증한다.
- 고유 값은 종류 정의의 **규칙표**(칸 이름, 값 종류, 범위, 기본값)로 검증한다. 백엔드는 규칙표를 실행 중에 읽고, 프론트도 같은 규칙표를 읽는다. 종류마다 Rust 구조체를 만들지 않는다.
- 값 종류에는 파일(이미지·사운드·글꼴)과 다른 요소 참조도 있다. 앱은 값 종류를 보고 다음을 알아서 한다.
  - 파일: 정리 대상에서 보호(지금 [asset_references.rs](../src-tauri/src/state/store/asset_references.rs)에 종류별로 추가하는 보호 집합을 대신한다), 프리셋에 파일 포함, 경로 고치기
  - 요소 참조: 복제·붙여넣기·삭제 때 참조 고치기
- 다른 칸 값에 따라 달라지는 검사 규칙은 함수가 아니라 정해 둔 데이터 문법으로 적는다. 백엔드가 읽어야 하기 때문이다.

### 3.4 문서 엔진 — **[확정]**

- 규칙표 해석과 일반 편집 동작(넣기, 빼기, 옮기기, 칸 값 바꾸기)을 Rust 엔진 하나로 쓴다. 검사·정리는 백엔드의 이 엔진만 한다.
- 편집 창의 화면 상태는 "확정 문서 + 아직 확정되지 않은 편집 목록"에서 만든다. 백엔드가 거부하면 그 편집을 목록에서 빼면 된다. 지금의 영수증·CAS 되돌리기 장치는 필요 없어진다.
- 백엔드는 바뀐 요소만 창에 보낸다.
- **[변경 2026-10-29] 창에는 엔진을 싣지 않는다.** 처음에는 편집 창이 WASM으로 같은 엔진을 실었지만, 측정에서 편집 창 메모리가 45MB 늘어 걷었다(9절 측정). 편집 창은 위치·값·묶음·공통 정보·넣기·빼기·옮기기를 JS로 화면에 먼저 반영하고(낙관 적용), 검사·정리된 결과는 백엔드 패치로 받는다. 그룹 묶기·풀기·입력·장면 연산은 패치를 기다린다.
- 지금 TS·Rust 두 벌인 편집 계산(동기화 데이터로 감시하는 것들)을 합치는 방법은 7단계에서 다시 정한다. 창에 엔진이 없으므로 WASM 한 벌로 합치는 길은 쓰지 않는다.

### 3.5 버전과 옮기기 — **[확정]**

- 종류마다 버전 번호가 있고, 문서에는 종류별 저장 버전을 적는다.
- 새 버전 정의에 옮기는 방법을 선언한다(칸 이름 바꾸기, 값 바꾸기, 새 칸 기본값). 선언으로 안 되면 코드 훅을 쓴다.
- 문서를 읽을 때 엔진이 최신 버전으로 맞추고, 저장은 항상 최신 버전으로 한다.
- 옛 앱이 더 새 버전 데이터를 만나면 그대로 보존하고 그 요소만 편집을 잠근다.
- 코드 훅은 TS로 쓰므로 백엔드가 직접 돌리지 못한다(3.8). 편집 창이 훅을 돌려 결과를 저장하고, 백엔드는 결과가 새 규칙표에 맞는지만 검사한다. 저장 전까지 백엔드는 옛 데이터를 보존하고, 오버레이는 같은 정의의 훅을 읽을 때 적용해서 그린다.
- 지금 불러올 때 도는 옮기기([normalization.rs](../src-tauri/src/state/migration/normalization.rs), [assets.rs](../src-tauri/src/state/migration/assets.rs))는 세 갈래다.
  - 값 바꾸기·기본값: 노브 감도 옛 기본값 1.40625를 1.0으로, 옛 글꼴 굵기 상태, 빈 글꼴 색 등. 선언으로 옮길 수 있다.
  - 값 종류 단위 정리: 색 rgba→hex, 숫자 범위 고치기, 이미지 모드·그라데이션 짝 정리, 끊긴 그룹 참조 지우기, 글꼴·이미지 파일을 앱 폴더로 옮기기와 경로 고치기. 앱이 값 종류를 보고 Rust에서 처리한다.
  - 칸 사이 계산이나 파일 읽기: 스프라이트 옛 `imageRect`를 `dx`·`dy`·크기에 합치고 옛 칸을 지우기(`migrate_legacy_sprite_positions_value`), 스프라이트 이미지 원래 크기 채우기. 코드 훅이 필요한 것은 이 갈래다.

### 3.6 그리기와 동작 — **[확정]**

- 종류마다 그리기 코드는 하나다. 데이터(자기 값, 입력 신호)는 앱이 창에 맞게 넣어 준다.
  - 편집 화면: 미리보기 데이터. 눌림 상태 색을 고치는 동안에는 "눌림" 미리보기를 넣는다(지금 [useEditStatePreviewStore.ts](../src/renderer/stores/grid/useEditStatePreviewStore.ts)가 하는 일).
  - 오버레이·OBS: 실제 신호. 신호는 복사하지 않고 그대로 넘겨서 지금과 같은 속도를 낸다.
- 동작 코드(그래프 기록 쌓기, 노브 회전 누적, 스프라이트 포즈 전환 등)는 오버레이·OBS에서만 돈다. 편집 화면은 정의에 적은 미리보기 상태로 그린다. `defineElement`의 `previewState`·`onMount`와 같은 방식이고, 편집 화면 모습도 지금과 같다.
- 앱이 넣어 주지 않는 데이터가 필요하면 종류 코드가 앱 내부를 직접 읽어도 된다. 그 부분의 편집 화면 미리보기는 종류가 챙긴다.
- 새 입력이 필요하면 앱이 넣어 주는 목록에 추가한다. 외부 종류도 같은 목록을 받는다.

### 3.7 패널 — **[확정]**

- 패널은 선언으로 만든다. 지금 패널 부품(`PropertySection`, `PropertyRow`, `NumberInput`, `ColorInput` 등)으로 그리므로 생김새와 동작이 현행과 같다.
- 기능 묶음은 자기 섹션을 갖고 있어서, 종류가 묶음을 쓰면 섹션이 붙는다.
- 선언 폭의 기준은 **지금 있는 내장 패널 전부**다. 종류 고유 값, 기능 묶음 섹션(키·노트·카운터 탭), 다중 선택 패널까지 선언만으로 쓸 수 있어야 한다.

|                | `defineElement` 지금             | 새 선언                                                                                                           |
| -------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 입력 종류      | 글자, 숫자, 체크, 색, 선택       | 비워 둘 수 있는 숫자, 그라데이션 색, 글꼴·굵기·스타일, 이미지, 사운드, 그림자, 회전, 키 지정, 축 지정 추가        |
| 값 모양        | 칸 하나에 값 하나                | 묶음 값(카운터 설정), 목록(스프라이트 포즈) 추가                                                                  |
| 배치           | 섹션                             | 탭(키·노트·카운터), 종류별 섹션 순서 추가                                                                         |
| 편집 동작      | 미리보기·되돌리기 없이 바로 반영 | 입력·드래그 중 미리보기, 끝낼 때 저장, Esc 되돌리기, 값 맞추기(예: 그래프 속도 100 단위), 눌림 상태 미리보기 전환 |
| 다중 선택      | 정렬·분배·간격만                 | 모든 칸, 섞인 값 표시                                                                                             |
| 직접 만든 부분 | 패널 안에는 못 넣고 모달만       | 칸 하나 단위로 패널 안에 끼움                                                                                     |

- 단일 선택 패널과 다중 선택 패널은 같은 선언에서 나온다. 선택 조합별 수작업 라우트는 없어진다.
- 패널 표시 조건(예: 선 그래프일 때만 평균선 표시)은 백엔드가 읽지 않으므로 TS 함수로 써도 된다.
- 섹션 순서는 종류가 정한다. 예를 들어 노브 패널은 지금처럼 축 매핑이 위치·크기보다 위에 온다.
- 내장 패널에 새 입력이 필요하면 그 패널 전용 화면이 아니라 선언 입력 종류로 추가한다. 외부 종류도 바로 쓸 수 있다.
- 공개한 뒤에는 입력 종류를 고치지 않고, 새 옵션이나 새 입력 종류를 추가하는 식으로 넓힌다.

### 3.8 정의의 원본 — **[확정]**

- **앱 구조**(공통 정보, 기능 묶음, 입력, 오류 코드 등)는 Rust가 원본이다. TS 타입은 Rust에서 만든다. 지금 손으로 맞추는 TS 사본(`keyPositionSchema`, `EDITOR_ERROR_CODES` 등)은 없어진다.
- **종류 정의**는 TS 파일 하나에 선언과 코드를 함께 쓴다.
  - 백엔드가 읽는 부분(규칙표, 옮기는 방법)은 순수 데이터여야 한다. 빌드할 때 이 부분만 뽑아서 Rust가 읽는다. 함수가 섞이면 빌드에서 막는다.
  - 그리기 코드에서 쓰는 값 이름과 타입은 선언에서 바로 따라온다.
  - 외부 종류는 플러그인이 등록될 때 같은 데이터를 백엔드에 보낸다. 그 전까지 그 종류의 요소는 모르는 종류로 보존한다.
- 백엔드는 앱이 켜질 때 창보다 먼저 문서를 읽고 복구한다. 그래서 내장 종류의 선언은 앱 시작 때 Rust가 바로 읽을 수 있어야 한다. 빌드 때 뽑은 데이터를 바이너리에 넣어 이를 만족한다.
- 택하지 않은 방법: 선언을 데이터 파일로, 코드를 TS 파일로 나누는 방법은 내장과 외부 종류가 쓰는 모양이 갈라진다. 정의를 Rust로 쓰는 방법은 외부 종류가 쓸 수 없다.

### 3.9 `defineElement` — **[확정] 껍데기 유지**

- 겉모양(부르는 방법, 옵션, 동작)은 그대로 두고 안쪽을 새 정의로 바꾼다. 기존 플러그인은 고치지 않아도 된다.
- 앱이 옛 정의를 새 정의로 바꿔 읽는다.
  - `settings` → 규칙표와 패널 선언
  - `template` → 그리기 코드
  - `onMount` → 동작 코드(오버레이에서만)
  - `previewState` → 편집 화면 미리보기
  - `contextMenu`, `maxInstances`, `resizable`·`preserveAxis`·`resizeAnchor`, `messages` 등 → 정의의 해당 항목
- 플러그인 저장소의 인스턴스(`plugin_data_{id}/instances`)는 처음 한 번 편집 문서로 옮긴다.
- 플러그인은 `storage.get('instances')`로 자기 인스턴스를 직접 읽을 수 있다. 쓰기는 `PLUGIN_INSTANCES_KEY_RESERVED`로 막혀 있지만 읽기·`keys()`·`hasData`는 열려 있다. 옮긴 뒤에도 이 읽기는 같은 모양으로 돌려준다.
- 플러그인의 `storage.clear()`는 `clearByPrefix('{id}/')`로 이어지고, 백엔드는 인스턴스 버킷까지 함께 지운다(1.6.1부터의 "모든 데이터 삭제" 약속, [plugin_storage.rs](../src-tauri/src/state/store/plugin_storage.rs)). 옮긴 뒤에도 `clear()`가 그 플러그인의 요소를 함께 지우게 한다.
- 옛 API는 지금 모양으로 고정하고 새 기능은 새 API에만 넣는다.

### 3.10 다른 공개 약속 — **[확정] 유지**

- **플러그인 데이터 API**는 새 문서 위의 변환으로 유지한다. 아는 종류만 옛 모양으로 보여 주고, 새 종류(커서 트래커 등)는 나타나지 않는다. 옛 모양으로 들어온 쓰기는 새 문서 편집으로 바꾼다.
  - 키·스탯·그래프·노브의 `getPositions`·`updatePositions`, `dmn.keys.updateWithPositions`
  - `dmn.editor.get`·`commit`·`onCommitted` (API 문서의 "키 구조는 반드시 함께 변경" 규칙 포함)
  - `dmn.layerGroups.get`·`update`·`onChanged` (그룹이 트리 폴더로 바뀌므로 옛 그룹 모양으로 변환)
  - 관련 변경 이벤트
- **사용자 CSS**는 새 그리기 코드도 지금과 같은 클래스 이름, data 속성, CSS 변수를 쓰게 하고 테스트로 고정한다. 기준은 [CSS 문서](content/ko/custom-css/)에 안내된 CSS 변수 41개와 선택자(`.counter[data-counter-state]`, `[data-state]`, `[data-knob-element]`, `[data-knob-indicator]`, `[data-sprite-element]`, `[data-key-image-layer]` 등)다. 문서 예시의 `.kps-graph`·`.my-key` 같은 클래스는 사용자가 속성 패널에서 붙이는 이름이라 약속이 아니다.
- 옛 데이터 API는 고정하고 새 기능은 새 API(트리 모양)에만 넣는다.

### 3.11 기본안 — **[확정]**

- **옛 버전으로 되돌릴 때**: 새 형식은 새 파일에 저장하고 지금 저장 파일은 건드리지 않는다. 지금 앱이 새 형식 파일을 읽으면 손상된 파일로 보고 복구하다가 데이터를 잃을 수 있기 때문이다. 옛 버전으로 돌아가면 업데이트 직전 상태가 열린다.
- **모르는 종류**(플러그인을 지웠을 때 등): 편집 화면에는 자리 표시 상자로 보인다. 옮기기, 크기 바꾸기, 삭제는 되고 고유 값은 그대로 보존한다. 오버레이에는 그리지 않는다.

## 4. 첫 새 종류: 커서 트래커 (이슈 #222)

새 구조 위에서 처음 정의하는 새 종류다. 옛 흔적이 없는 종류로 정의 형식을 처음부터 끝까지 검증한다. 옛 데이터 API에는 나타나지 않는다.

**[확정]** 두 모드를 옵션으로 고른다. UI 이름은 "커서 트래커"다.

|         | A. 이동량 모드                                        | B. 화면 위치 모드                                        |
| ------- | ----------------------------------------------------- | -------------------------------------------------------- |
| 입력    | 마우스 하드웨어 이동량(dx, dy)                        | 전역 커서 좌표(x, y)                                     |
| 점      | 이동량 × 감도만큼 밀렸다가 중앙으로 돌아옴, 짧은 궤적 | 모니터 영역을 패드에 대응                                |
| 비율    | 해당 없음(x·y 같은 배율, 경계에서 잘라냄)             | 고정(패드 크기를 모니터 비율로 잠금) / 자유(늘려 채우기) |
| 영역 밖 | 해당 없음                                             | 점을 숨기고 궤적을 끊음                                  |

**[제안]** 세부 설계에서 확정한다.

- 모니터(B 모드): 기본은 주 모니터, 특정 모니터 선택 가능. 저장한 모니터가 없으면 주 모니터로 대체한다.
- 공통 옵션: 궤적 유지 시간(ms 기준), 점 크기·색, 궤적 색·두께. 배경·테두리는 기능 묶음으로 붙인다.
- 입력: 마우스 이동량과 커서 좌표를 앱이 넣어 주는 목록에 추가한다. 백엔드에서 이동량을 모아 60~120Hz 수준으로 묶어 보낸다(노브의 `AXIS_THROTTLE_MS` 묶음 전송과 같은 방식).
- OBS: 새 이벤트는 `FORWARDED_EVENTS`에 등록하고 `publish_event`로 발행한다. 모니터 목록 커맨드를 OBS에서 쓰려면 `ALLOWED_WS_COMMANDS`에 추가한다.
- 실제 기기에서 확인할 점: macOS 이동량 읽기, macOS 전역 좌표(포인트)와 Tauri 모니터 좌표(물리 픽셀) 변환.

### 전환 방식 [구현 중 정함]

- store가 트리 문서를 들고, 옛 종류(키·스탯·그래프·노브·스프라이트)는 아직 옛 모양 경로가 쓴다. 영속 커밋마다 옛 모양이 바뀌었으면 트리에 맞춘다(바뀐 탭·바뀐 요소만). 트리에만 있는 정보(새 종류 요소, 그룹 숨김)는 지킨다.
- 트리 쓰기(`element_document_commit`)는 트리에만 있는 요소와 그룹 숨김만 고칠 수 있다. 옛 종류 요소·그룹 구성은 `MANAGED_ELSEWHERE`로 거부한다. 종류를 옮기면 이 제한이 풀린다.
- 기능 묶음은 손으로 쓴 구조체 대신 Rust에 적은 규칙표로 검사한다(값 종류 기계를 같이 쓴다). 카운터 설정·노트 색 조합처럼 안쪽이 복잡한 값은 앱 전용 `json` 값 종류로 두고 앱 타입이 검사한다.
- 옛 종류의 값은 읽기 정리에서 건드리지 않는다(옛 정규화가 맡는다). 규칙표가 더 엄격해 저장 값이 바뀌는 일을 막는다.
- 창 전달: 발행 지점(`publish_event`) 한 곳에서 트리 리비전을 잠금 없이 비교하고, 바뀌었으면 구조가 바뀐 장면은 통째로, 값만 바뀐 장면은 바뀐 요소만 보낸다.
- 저장: 트리 문서의 옛 종류 요소는 id·종류·위치·자리 정보만 저장하고, 읽을 때 옛 모양 배열에서 다시 채운다.
- 편집 창은 커밋을 하나씩 보낸다(백엔드는 동시에 온 커밋의 순서를 지키지 않는다). 화면 반영은 낙관 적용으로 즉시 한다.
- 되돌리기: 트리 쓰기를 기존 히스토리에 기록한다. 기록은 트리에만 있는 요소 + 옛 요소의 id 뼈대라서, 그 사이 옛 경로 편집은 되돌리지 않는다.

### 종류별 UI 이전 순서 조정 [구현 중 정함, 2026-10-30]

- 노브 편집 화면을 트리 편집기로 옮겨 보니 옛 선택과 트리 선택이 서로 배타라(한쪽을 고르면 다른 쪽을 비운다) 키와 노브를 함께 고르기·마퀴·섞인 옛 그룹 선택·그룹 회전이 깨졌다. 트리 편집기에는 회전·피벗·그룹 회전 손잡이도 아직 없다.
- 그래서 편집 화면은 종류 단위로 옮기지 않는다. 선택·끌기·그룹·마퀴·레이어 목록은 모든 옛 종류를 한 번에 옮길 범용 단계로 미루고, 그때까지 옛 경로가 맡는다(현행 유지).
- 상호작용이 없는 오버레이·OBS 그리기는 종류 단위로 트리에서 그린다(`TREE_OVERLAY_KINDS`). 정의의 `legacyOverlay`가 옛 오버레이 그리기를 옛 위치 객체 어댑터(`legacyPositionOf`)로 받아 그대로 쓴다. 오버레이 창 크기 계산은 아직 옛 배열이 맡는다.

### 옛 배열 완전 제거(B) 단계 [2026-10-30 사용자 결정]

옛 배열을 메모리 보기로 남기는 안(A) 대신, 소비자를 모두 트리 모양으로 바꿔 배열을 없앤다. 옛 상호작용 코드(약 1만 6천 줄, 테스트 다수)는 버리지 않고 id·트리 기준으로 한 모듈씩 바꾼다. 단계마다 앱이 지금처럼 동작하는 상태로 커밋한다.

1. **선택 하나로**: 옛 선택 스토어에 트리 요소 가족(`document`)을 더하고 상호 배타를 없앤다. 트리 선택은 거기서 파생한다. 플러그인 요소(`plugin`)가 이미 같은 방식으로 섞여 있다.
2. **`document` 가족 기능 맞추기**: 끌기·크기·회전·그룹 회전·방향키·삭제·복사·정렬·겹침 순서·그룹·메뉴·패널을 섞인 선택에서 지원한다(플러그인 영수증 방식).
3. **종류별 전환**: 옛 종류를 `document` 가족으로 하나씩 옮긴다(그리기는 정의, 패널은 선언+묶음 섹션, 쓰기는 트리 연산 → 백엔드가 옛 편집 커밋으로).
4. **프론트 옛 배열 제거**: 플러그인 API는 필요할 때만 옛 모양으로 바꾼다.
5. **백엔드 Rust 소비자를 트리로**: 입력 매핑·카운터·사운드·편집 커밋·히스토리. 그 뒤 옛 배열 제거.
6. **재측정**

### B 1~3단계 진행 [2026-10-30]

- **선택 하나로**: 옛 선택과 트리 선택은 하나의 선택이다. 바꿔 고르기는 다른 쪽을 비우고(옛 선택 스토어의 바꿔 고르기 동작이 직접), 넣고 빼기·마퀴·옛 그룹째 고르기는 다른 쪽을 지킨다(`keepOtherSelection`). 끌기는 옛 수명 주기에 트리 요소 영수증을 더하고, 키보드는 옛 처리기 뒤에 트리 처리기를 부른다(`afterKeyDown`).
- **한 동작 한 되돌리기**: 트리 커밋도 동작 id를 받아 맨 위 기록(옛 편집·플러그인·트리)에 합친다(Compound에 트리 뼈대). 옛 편집 커밋으로 가는 트리 쓰기가 트리 전용 노드도 바꾸면 그 뼈대를 같은 기록에 담는다. 같은 동작으로 제자리로 돌아온 몫은 빼고 비면 기록째 지운다.
- **트리 요소 가족 기능**: 회전·묶음 회전·묶음 크기 조절(요소 최소 크기, 되돌리기 취소)·한 칸 앞뒤, 섞인 선택의 묶음 회전·크기 조절(두 가족을 감싸는 틀, 같은 동작 id).
- **종류 전환(`TREE_EDITED_KINDS`, 노브부터)**: 편집 화면에서 그 종류를 트리 요소 가족이 맡는다. 데이터는 관심사별로 나눈다 - 위치·크기·회전·구조는 트리로 쓰고 감싸는 상자를 트리에서 그린다. 겉모습 칸은 옛 패널 처리기로 옛 경로에 써 옛 모양 보기가 낙관 반영하고, 편집 화면 얼굴이 그 값과 미리보기를 그린다(패널을 그대로 재사용). 겉모습 칸을 트리로 옮기는 건 4단계(`legacyFieldPatch`로 옛 패널 패치 → 트리 연산).
- **읽기 정규화**: 정의에 묶음·칸이 늘면 그 전에 저장한 옛 종류 요소의 칸을 읽을 때 옛 칸에서 제자리로 올린다(`lift_legacy_kind_fields`). 노브 이미지 묶음이 이 위에 있다.
- **남은 틈**: 레이어 패널은 옛 그룹 안의 트리로 옮긴 요소를 트리 구역에 따로 보인다(레이어 패널 통합에서 해결).
- **옛 선택 동작과 합친 선택**: 트리로 옮긴 종류는 트리 선택에 있으므로, 옛 선택을 읽는 동작(레이어 우클릭·여러 행 끌기·지우기·묶기·일괄 패널)은 옛 선택 모양으로 합친 선택(`document/treeEditedSelection.ts`)을 쓴다. 옛 선택 해제는 트리 선택도 비운다.
- **공통 커밋 경로의 트리 몫**: 섞인 연산은 트리 몫과 옛 몫에 같은 동작 id를 붙이고, 생성기 연산은 직렬 슬롯 안에서 만든 뒤 나눈다. 플러그인 섞인 거래는 원자성을 위해 트리 몫을 따로 빼지 않는다(백엔드 동기화 뒤 반영).
- **패널 선택 규칙 하나**: 옛 속성 패널이 트리로 옮긴 종류를 함께 보는 조건(트리 선택이 모두 그 종류, 플러그인 없음)은 `panelSelectionOf` 하나다. 일괄 패널·그라데이션 축·편집 화면 얼굴의 일괄 미리보기가 같은 선택을 본다.
- **전환한 종류**: 노브, 그래프, 스탯, 스프라이트, 키(2026-10-30) - 편집 화면의 옛 종류 전부. 옛 편집 경로에는 플러그인만 남는다(오버레이의 키는 아직 옛 그리기). 편집 화면 얼굴은 옛 모양 보기를 나눈 `KnobFaceView`·`GraphFaceView`·`KeyFaceView`(스탯·키)·`SpriteFaceView`.
- **종류 정의의 편집 화면 선택지**: `faceOwnsClassName`(옛 그리기에서 클래스가 상태 속성과 같은 노드 - 그래프·스탯), `editorHandles`(종류 전용 손잡이 - 스프라이트 회전), `occupiedResizeHandle`(비울 크기 조절 자리 - 스프라이트 기준점), `lockAspect`.
- **곁 레이어**: 옛 목록으로 그리던 바깥 카운터·스프라이트 기준점/자세 손잡이는 `useTreeFramedPositions`로 트리 틀(끌기·옛 패널 미리보기 포함)을 따른다.
- **옛 동작을 그대로 쓰는 것**: 트리로 옮긴 종류 하나의 우클릭은 옛 항목 메뉴, 여럿은 섞인 메뉴, `]`·`[`는 옛 계획(그룹을 넘는 전체 겹침 순서). 붙여넣기의 스프라이트 자세 규칙은 옛 붙여넣기와 같은 순수 함수.
- **React Compiler**: 렌더 중 트리 스토어·프리뷰 오버레이를 읽는 파일은 `'use no memo'`(인자만으로 캐시돼 화면이 안 따라온다).
- **끊긴 참조 허용 [2026-10-30 사용자 결정]**: 트리 엔진은 없는 요소를 가리키는 참조(지운 키를 가리키는 스프라이트 트리거, 함께 붙이는 키보다 먼저 도착한 삽입)를 받는다. 있는 요소를 가리키면 종류는 계속 검사한다.
- **크기와 함께 맞출 값**: 정의 선택지 `resizeValues`(스프라이트 기본·자세 이동값 비례)를 트리 쓰기 입구 두 곳이 붙인다. 이동값과 비율 기준 크기는 같은 곳(옛 스토어 우선)에서 읽는다.
- **받아들인 틈(스프라이트)**: 여러 개 회전·크기 조절의 기준점은 상자 기준(옛 방식은 그림 이동값 포함). 키와 섞인 묶음 크기 조절은 닫는다. 트리거가 다른 종류(플러그인이 넣은 스탯 id 등)를 가리키는 스프라이트는 트리 편집이 거부된다(드묾).
- **지우기·읽기도 끊긴 참조를 남긴다(키 전환)**: 트리로 키를 지워도 스프라이트 트리거에서 빼지 않고, 불러오기 정규화도 끊긴 참조를 남긴다(있는 요소의 다른 종류만 비운다). 옛 계약(패널의 '삭제된 키')과 같고, 자세 트리거가 비어 옛 검증이 키 지우기를 거부하던 문제를 막는다. 지운 키를 되돌리면 트리거가 다시 이어진다.
- **쌓임 순서**: 편집 화면의 트리로 옮긴 옛 종류는 옛 층처럼 낙관 반영된 옛 컬렉션의 자기 zIndex로 플러그인 요소와 같은 축에 쌓고, 플러그인 요소보다 먼저 그린다(같은 값이면 플러그인이 위). 흩어진 옛 그룹은 트리에서 모이므로 트리 순서로 zIndex를 정하지 않는다. 트리에만 있는 종류는 바로 아래 옛 종류 요소의 값을 따른다.
- **Shift 범위 선택**: 트리 요소도 옛 키처럼 마지막으로 누른 요소 영역(`lastSelectedKeyBounds`, 플러그인 요소와 공유)부터 범위 안의 트리 요소와 플러그인 요소를 고른다.
- **옛 경로 테스트**: 키를 옛 종류 대표로 쓰던 옛 선택·끌기·레이어 테스트는 `__tests__/legacyKeyKinds.ts` 목으로 키만 옛 경로에 남겨 돌린다. 옛 경로를 걷을 때 함께 걷는다.
- **받아들인 틈(4단계 전까지)**: 트리로 옮긴 종류가 섞인 일괄 패널은 회전 줄을 닫는다(캔버스의 섞인 회전 손잡이를 쓴다). 플러그인이 섞이면 일괄 패널로 잇지 않는다. 섞인 메뉴의 맨 앞·뒤와 플러그인 섞인 지우기는 트리로 옮긴 종류를 옛 계획·거래에 함께 넣어(옛 그룹을 넘는 전체 순서, 원자성) 편집 화면 반영이 백엔드 왕복 뒤다. 생성기 다시 시도에서 옛 몫이 사라진 드문 경우 결과 보고가 처음 만든 트리 몫과 다를 수 있다. 편집 세션 대상(`getEditSessionTarget`)과 편집 동작 조절기의 선택 구독은 옛 선택만 봐서, 트리로 옮긴 종류끼리 선택을 바꿔도 세션이 취소되지 않는다(노브·스탯부터 있던 틈, 4단계에서 선택을 하나로 합칠 때 정리).

### 4단계 진행 순서 [구현 중 정함, 2026-10-30]

겉모습 쓰기만 트리로 옮기면 옛 스토어를 읽는 곳(편집 화면 얼굴·패널·카운터 등 100여 곳)이 백엔드 왕복 전까지 옛 값을 보고, 읽기만 옮기면 옛 경로로 쓴 값이 왕복 전까지 안 보인다(낙관 반영이 깨진다). 그래서 다음 순서로 한 커밋씩 옮긴다.

1. **대기 중인 트리 편집 얹기(4단계 동안만 쓰는 다리)**: 트리로 보낸 겉모습 편집의 옛 칸 값(`legacyFieldPatch` 결과 - 보내는 값과 같다)을 미리보기와 같은 읽기 합성 층(`composePreviewPositions`)에 얹는다. 옛 스토어의 canonical과 코디네이터 문서는 건드리지 않는다 - 코디네이터가 스토어를 읽어 칸 단위로 비교·커밋·되감기를 하므로(`flush`의 스냅샷 비교, 거부 되감기, 동결 의도 재적용), 스토어에 얹으면 같은 칸이 옛 커밋으로 또 나가고 되감기 소유가 틀어진다. 트리 커밋이 거부되면 바로 내리고, 확정되면 트리 스토어가 그 revision의 변경을 받은 뒤(백엔드는 옛 편집 이벤트를 먼저 보낸다) 코디네이터 이벤트 큐가 빌 때 내린다. 트리로 가는 옛 칸 패치(숨김·이름·회전 포함)는 모두 이 층이 얹고 옛 스토어 먼저 쓰기에서 뺀다 - 커밋 나누기와 같은 판정(`routeForTree`). 트리 몫 커밋은 반영된 뒤 끝난다(분리된 패널의 미리보기 취소가 메인 창 반영보다 앞서지 않게). 거부되면 대기 편집을 내리고 오류로 올린다(호출자가 알린다) - 옛 경로로 다시 보내면 뒤에 줄 선 편집을 덮을 수 있다. 트리 변경 이벤트를 놓쳐도 쓰기 대기(종료·패널 붙이기 등)가 멈추지 않게 반영 기다리기에 3초 시한을 둔다. 미리보기 투영처럼 지금 값에서 다음 값을 계산하는 곳은 `captureEditorView`(대기 편집까지 얹은 문서)를 읽는다.
2. **겉모습 쓰기를 트리로**: 옛 패널 패치를 `legacyFieldPatch` → `legacyPatchOps`로 트리 연산으로 보낸다. 정의·묶음에 없는 칸(스탯·그래프·노브가 키 모양에서 물려받은 쓰지 않는 칸)은 옛 경로에 남긴다.
3. **읽는 곳을 트리 직접 읽기로**: 선택·미리보기를 id 기준으로(창 사이 미리보기 방송의 인덱스 → id), 편집 화면 얼굴·카운터·패널·가이드·미니맵을 영역별로.
4. **오버레이 키**(실시간 입력 경로, 따로 리뷰·측정), **레이어 패널 통합**.
5. **걷기**: 1의 다리, 옛 스토어·옛 편집 커밋의 옛 종류 경로, `legacyKeyKinds` 목 테스트. 플러그인 API(`dmn.keys` 등)는 트리에서 필요할 때 옛 모양으로 만든다.

#### 4단계 진행 [2026-10-30]

- **끝난 것**: 대기 중인 트리 편집 층, 겉모습·숨김·이름·회전 쓰기와 스프라이트 필드 패치(`commitTreeLegacyFields`, 이동값 비례 없음)를 트리로, 편집 미리보기 계약을 요소 id로(미리보기 계약 2), 편집 화면 얼굴 다섯 종류가 트리 값 + 요소 미리보기(`useTreeElementPosition`)를 읽음, 오버레이·OBS 키를 트리에서(`legacyOverlay`, 이름·입력은 트리 입력 슬롯), 편집 세션 지문·편집 제스처 취소가 트리 선택 전환도 본다(`keepOtherSelection`의 다른 쪽 선택 읽기·알림), 그래프 이미지 묶음.
- **옛 경로에 남은 쓰기**: 키 매핑(`setKeySlot` - 매핑 배열을 읽는 패널·카운터와 함께 옮긴다), 묶기·풀기·겹침 순서·레이어 패널(옛 계획), 정의·묶음 밖 옛 칸, 창 blur·종료 경계의 제스처 정산(`commitPendingAsync` - 정산 순간 한 프레임 옛 값이 보일 수 있다).
- **남은 읽기**: 속성 패널(옛 배열 순번), 바깥 카운터·노트 트랙(옛 배열), 레이어 패널, 플러그인 API, 붙여넣기·클립보드의 옛 종류 경로(이미 트리 클립보드가 옛 종류도 붙인다 - 걷기만), 가이드·미니맵·마퀴의 옛 반복(옛 종류가 없어 비어 있다 - 걷기만).

#### 플러그인 인스턴스를 트리로 [구현 중 정함, 2026-10-31]

- **A(끝)**: 플러그인마다 외부 종류 `plugin:{id}`를 등록한다(값 칸은 검사 없는 json, 회전 없음). 등록 전·뺀 뒤는 모르는 종류로 보존.
- **B**: 인스턴스 버킷(목록을 읽고 쓰는 단일 입구)의 저장 위치를 트리 장면으로 옮긴다. 프론트 플러그인 런타임은 지금처럼 목록을 주고받는다.
  - 요소 id는 `{pluginId}::{instanceId}`(프론트 fullId와 같다 - 플러그인 사이 instanceId 중복이 합법이라). 장면은 탭, 틀은 위치·측정 크기, 값은 설정, 숨김은 공통 정보. 목록 순서·겹침 순서(zIndex)·그룹 소속·측정 크기 유무는 요소에 저장된 원본 인스턴스 그대로 돌려준다(목록 왕복이 정확히 같다 - 트리 자리는 E 전까지 쓰지 않는다).
  - 플러그인 요소는 옛 모양 다시 만들기(이웃을 따라 붙이기)에서는 트리 전용 노드처럼 보존되지만, 트리 기록 뼈대·되돌리기 떼기·프리셋 트리 정보에서는 빠진다(`is_plugin_kind`). 플러그인 쓰기는 지금처럼 플러그인 기록이 맡는다 - 트리 기록이 장면의 트리 전용 노드를 통째로 되돌리므로, 플러그인 노드를 함께 잡으면 두 기록이 서로를 덮는다. 문서를 새로 만드는 경로(전체·탭 프리셋, 기록에서 옛 모양으로 장면 다시 만들기)는 이전 문서의 버킷을 옮겨 싣는다(`carry_plugin_buckets`). 읽을 때는 요소 id·탭이 원본 항목과 맞는 노드만 인정한다(복제된 사본 무시).
  - 저장소 공개 API(`get('instances')`·`keys()`·전체·접두어 지우기)와 프리셋 기록 패치·자산 정리는 버킷을 옛 키 모양으로 본다. 프론트는 플러그인 종류(`isPluginKind`)를 트리 슬롯·레이어 트리 행·트리 편집기 판정에서 뺀다(옛 플러그인 렌더러가 그린다).
  - 처음 불러올 때 한 번 옮긴다(표식 `pluginInstancesImported`, 버킷 키 제거, 같은 영속 한 번). 해석 못 한 항목·없는 탭의 인스턴스는 문서 바깥 칸에 원본으로 보존.
- **E(다음)**: 묶기·풀기·맨 앞·뒤·한 칸·레이어 끌기를 옛 계획 없이 트리 연산(Group·Ungroup·Move) 하나로 옛 종류·플러그인·트리 전용 종류를 함께 다룬다(흩어진 그룹 모으기는 문서 45행에서 받아들임).
  - 플러그인 항목의 zIndex·groupId는 계속 기준이다. 버킷을 쓸 때 그 값으로 트리 자리(부모 그룹·형제 사이 겹침 순서)를 정하고, 트리 연산이 플러그인 노드를 옮기면 옛 종류 zIndex 맞추기(`moved_z_fixes`)에 플러그인 노드를 같은 축으로 넣어 새 zIndex·groupId를 항목에 쓴다. 그 커밋 기록에 바뀐 플러그인의 플러그인 기록 스냅샷을 함께 담고(한 되돌리기), 플러그인 모델 revision을 올려 `pluginInstances:changed`를 보낸다. 트리 기록은 계속 플러그인 노드를 보지 않는다(기록 한 갈래).
  - 1·2(끝): 버킷을 쓸 때 항목 값으로 자리를 정하고(값이 그대로면 노드는 제자리), 트리 커밋(트리 전용·옛 편집 두 경로 모두)은 옮긴 장면의 플러그인 노드를 `sync_plugin_entries_from_tree`로 맞춘다 - 아래쪽 옛 종류·앞 플러그인 값 이상이고 바로 위 옛 종류 값 미만이면 그대로, 아니면 사이 값(실수). zIndex 없는 항목은 위에 옛 종류가 없으면 그대로(맨 위). groupId는 가장 가까운 옛 그룹(트리 전용 그룹은 건너뜀). 옛 편집 경로는 계획 때 본 플러그인 모델 revision이 커밋 때와 다르면 충돌로 돌려보내 다시 계획한다(트리에 실린 목록이 낡지 않게).
  - 3(다음): 프론트 구조 편집을 트리 연산으로.
- **C·D·F**: 런타임이 트리를 직접 읽고 쓰기(플러그인 기록을 트리 기록으로) → 플러그인 요소를 트리 선택 가족으로 → 옛 플러그인 경로 걷기.

### 받아들인 동작 (리뷰 6회차까지)

- 레이어 패널의 트리 요소 행은 옛 목록 아래에 겹침 순서대로 둔다. 옛 행 사이에 끼우면 옛 끌기 계산(행 높이 × 순번)이 어긋나기 때문이다.
- 옛 구조가 바뀌어 트리를 다시 맞출 때, 트리 요소는 살아남은 가장 가까운 아래 옛 요소(또는 옛 멤버 없는 그룹)를 따라간다. 한 커밋에 여러 구조 변경이 겹치면 트리 요소끼리 위아래가 바뀔 수 있다.
- 옛 요소 삭제를 되돌리면 트리 요소가 되살아난 요소 아래에 놓일 수 있다.
- 옛 멤버가 없는 그룹은 옛 구조가 바뀌면 장면 맨 위로 올라간다(옛 모양 가져오기 규칙).
- 아래에 옛 요소가 없는 트리 요소는 가장 낮은 옛 요소와 같은 zIndex로 그 앞에 그린다. 옛 요소가 음수 zIndex면 불투명 배경 뒤에 가려지는 것도 옛 요소와 같다.
